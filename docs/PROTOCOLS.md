# Протоколи та дані

## MQTT

Підписка backend: `greenhouse/+/telemetry`, QoS 1. Приклад топіка: `greenhouse/bed-a/telemetry`.

```json
{"metric":"soil_moisture","value":24,"ts":1795478400000}
```

Допустимі метрики: `temperature`, `humidity`, `soil_moisture`, `light`. `value` — скінченне число; `ts` — невід’ємне ціле Unix ms, за відсутності підставляється час сервера. Ідентифікатор пристрою береться з топіка. Bridge не виконує фізичної валідації діапазону кожної метрики, дедуплікації MQTT або керування клапаном. Невалідні повідомлення журналюються, до SQLite не додаються.

## Socket.IO

Клієнт підключається до backend через `/socket.io`, передає `auth.token` (access JWT). Подія `bed:subscribe` приймає ідентифікатор формату `[a-zA-Z0-9_-]{1,64}`; сервер повертає ack `{ok:true,bed}` або `{ok:false,error:"Invalid bed"}`. Попередня кімната `greenhouse:<id>` залишаєтьcя. Подія `telemetry:update` надсилається після INSERT:

```json
{"device_id":"bed-a","bed_id":"bed-a","metric":"soil_moisture","value":24,"ts":1795478400000}
```

Вебклієнт перепідключається, повторно підписується та інвалідує REST-кеш обраної грядки після відновлення зв’язку. При завершенні JWT сервер розриває socket, клієнт намагається оновити access token. У разі невдалого refresh потрібно увійти повторно.

## REST та зберігання

[OpenAPI](openapi.yaml) описує 10 операцій на 9 шляхах. `telemetry` має індекс `(device_id, metric, ts, id)`. REST підтримує курсор `ts:id`, типову сторінку 500, максимум 1000 записів; погодинна агрегація `avg` доступна лише для `soil_moisture`. `alerts` повертає періоди низької вологості, а не підтверджені поливи. Автоматичного TTL для телеметрії немає; історію обмежує наявний обсяг БД.
